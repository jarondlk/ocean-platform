**Verdict: v0.4.5 is not release-ready.** The short citation labels reduce token
pressure, but repeated live tests expose a citation-format regression. Existing
production also has a scientific-scope bug and misleading trust presentation.
No application fixes, commits, release, or production deployment were made as
part of this QA pass.

## Confirmed findings

### QA-01 — P1: valid citation ranges cause candidate request failures

The model sometimes writes `[S1–S8]`, `[S9–S13]`, or `[S1, S3–S8]` instead of
listing each source separately. All referenced labels exist in the diagnosed
requests, but `CitedPrompt.resolve` only accepts comma/semicolon lists and rejects
ranges. The model finishes with `STOP`; the API then returns
`502 llm_invalid_citation` and discards the answer.

Observed failures across the matrix and targeted repeats:

| Question family | Citation failures / trials |
| --- | --- |
| Original eDNA request | 1 / 6 |
| MiFish versus shotgun | 2 / 6 |
| CTD/SST agreement with context | 4 / 4 |

Four failures in the diagnostic batch have retained raw text proving the range
syntax cause. The initial three failures did not retain raw model text, so their
exact rejected syntax is not asserted. The counts are targeted observations,
not population failure-rate estimates.

Reproduce with the original, `mixed_sources`, and `legacy_context` questions in
[the QA matrix](../evaluation/qa/issue59_v045.json). Relevant code:
[`orchestration/citations.py`](../orchestration/citations.py),
[`api/main.py`](../api/main.py).

Fix acceptance: support an explicit, bounded citation grammar and consistently
render/audit it. If ranges are supported, every expanded label must exist in the
request map; invented endpoints, gaps, reversed/excessive ranges, and malformed
syntax must remain rejected. A prompt-only instruction is insufficient evidence
of robustness.

### QA-02 — P1: global context bypasses explicit scientific scope

Question: **“Summarize CTD seasonal temperature trends and satellite SST
agreement in this date range.”** Settings: CTD, From **2099-01-01**, To
**2099-12-31**, analysis/reliability on.

Both production and candidate return an answer about 2024–2026 with zero primary
or linked documents. The candidate injects nine global analysis/reliability
documents. Production shows **Strong / 100%, zero warnings**. The selected date
range is not included in the generation prompt. The eDNA equivalent correctly
abstains without invoking the model.

`build_prompt_with_context` uses global legacy context selected by query keywords;
its date/bay/sample filters do not constrain that context. Relevant code:
[`orchestration/unified.py`](../orchestration/unified.py),
[`api/main.py`](../api/main.py).

Fix acceptance: scope supplementary evidence alongside primary retrieval; include
explicit scope in the prompt. For an empty scope, abstain or clearly segregate
out-of-scope background. Add date, bay, sample, and source-family regressions.
Only the date manifestation was exercised live in this pass.

### QA-03 — P1: “Strong” trust is not evidence of scientific correctness

The deterministic audit checks source membership and coverage, not whether a
source supports a claim. With evidence “temperature was 12 C,” a synthetic answer
“temperature was 999 C [ctd_qa]” scores **Strong / 100%**. A valid citation plus
one invented source still scores **Strong / 85%** because one invalid reference
subtracts only 0.15 and the strong threshold is 0.85.

The live out-of-scope answer in QA-02 demonstrates the practical risk. Relevant
code: [`orchestration/answer_audit.py`](../orchestration/answer_audit.py),
[`frontend/app/chat/page.tsx`](../frontend/app/chat/page.tsx).

Fix acceptance: present citation/coverage checks as such; do not present them as
claim verification. Invalid citations and scope violations must prevent a strong
rating. Any claim-support check needs separate validation.

### QA-04 — P2: omitted prompt documents are still considered supplied evidence

A synthetic eight-document request with 8,000 characters per document exceeds
the 32,000-character evidence-section bound. Only four source headers survive,
but the response ledger/audit retain all eight documents. A canonical citation
to omitted `ctd_7` is accepted as valid and can score Strong / 100%.

The alias map itself excludes omitted headers; the later audit still receives
the original unbounded rows. Relevant code: prompt bounding in
[`orchestration/unified.py`](../orchestration/unified.py), source accounting in
[`api/main.py`](../api/main.py), and the audit index.

Fix acceptance: persist and audit the actual supplied evidence, with explicit
omission/truncation metadata. A retrieved document is not necessarily a document
the model received. This boundary was reproduced deterministically, not observed
in the small live pilot requests.

### QA-05 — P2: internal standards are omitted, then inferred absent

Question: **“Do these MiFish results establish contamination-free water or
calibrated fish abundance? Explain what the sample classification and
internal-standard evidence permit us to conclude.”** Settings: eDNA source.

All three trials reject contamination-free/calibrated-abundance claims, but one
adds: “Consequently, internal quantitative standards are absent or unrecorded”
after observing zero copies/mL. Another says internal standard controls are
missing. The deployed sample page actually lists four standard records:

| Standard | Read count |
| --- | ---: |
| MiFish_STD_01 | 7,327 |
| MiFish_STD_02 | 16,651 |
| MiFish_STD_03 | 29,624 |
| MiFish_STD_04-2 | 59,676 |

Those rows are absent from the two retrieved eDNA summaries. Missing copies/mL
is not evidence that standards do not exist. Their presence alone also does not
prove calibration. Relevant code:
[`retrieval/edna_document_builder.py`](../retrieval/edna_document_builder.py).

Fix acceptance: expose the available standard evidence with provenance, or state
that the current retrieved context cannot establish it. Keep “missing from the
retrieved context,” “absent from the source,” and “not calibrated” distinct.

### QA-06 — P2: audit and Markdown navigation disagree

`[ctd_qa](https://example.org/qa)` is counted as a valid citation by the audit but
renders as an ordinary external link, bypassing the evidence inspector.
Code-formatted `[ctd_qa]` likewise counts but is not navigable. Plain, bold, and
grouped canonical citations work. Unsafe JavaScript links and raw HTML remain
non-executable in the renderer probes.

Relevant code: [`frontend/components/MarkdownAnswer.tsx`](../frontend/components/MarkdownAnswer.tsx)
and [`orchestration/answer_audit.py`](../orchestration/answer_audit.py).
Fix acceptance: use consistent Markdown-aware citation parsing and rendering;
source-looking link labels must not imply a validated external destination.

### QA-07 — P2: failed-request diagnostics are lost in the UI

Reversed From/To dates are correctly rejected, but the production browser renders
the entire validation JSON and echoed request instead of a concise field error.
The frontend also converts structured model errors to a plain `Error(message)`,
losing the error code and interaction ID required to correlate a report.
The new output-limit guidance itself renders correctly in candidate replay.

Relevant code: [`frontend/lib/api.ts`](../frontend/lib/api.ts).
Fix acceptance: retain structured error fields and render validation arrays as
human-readable messages, with a usable failure reference.

### QA-08 — P3: whitespace-only API questions invoke chat

`POST /chat` with `query: "   "` is accepted and can be persisted as answered.
The UI blocks blank submissions, but API validation only checks string length.
Reversed dates, incompatible eDNA filters, excessive Top-K, and excessive output
limits were all correctly rejected.

Relevant code: [`api/schemas.py`](../api/schemas.py).
Fix acceptance: trim and reject empty questions before retrieval or persistence.

## Scientific answer review

The detailed QCauto comparison matched the supplied 35 detections and 9,635
reads per method and correctly distinguished Siganus genus/species assignments.
The leading 19,270-fish question correctly rejected summing reads into fish counts
or claiming independent validation. The unsupported `[S999]` instruction was
ignored in its live trial, while synthetic unknown-label outputs failed closed.

Successful original answers do not always state explicitly that two records are
one physical sample. Mixed-source answers preserve geographic/time separation
but introduce broad assay/ecological descriptions beyond the cited summaries.
The Japanese answer gives one sample and two methods correctly but adds an
unsupported read-count-difference statement and contains a mixed-language typo.
These remain quality issues even when citation identifiers are valid.

## What passed and what remains

All 27 candidate requests produced matching isolated lifecycle records:
successful answers match saved answers; failures have failed status and no saved
answer. Empty eDNA scope avoids generation. Forced 32-token truncation produces
`llm_output_limit`, not a successful partial answer. Existing authentication,
ownership, feedback, validation, and failure regressions passed; PostgreSQL
migration and chat lifecycle checks passed too.

Before release, fix QA-01 through QA-07 and add targeted regressions, then rerun
the affected live questions and candidate browser flows. QA-08 is a small API
validation fix. This pass is not a concurrency/load benchmark, a formal security
assessment, or an exhaustive scientific validation of every corpus record.
Temporary QA services and the disposable database are cleaned up after review.

Reproducible local probes:

```sh
.venv/bin/python -m evaluation.qa.probe_chat_contract
node evaluation/qa/probe_markdown.cjs
```

The live runner is [`evaluation/qa/run_chat_system_qa.py`](../evaluation/qa/run_chat_system_qa.py).
Run it only in the configured candidate environment with the verified chat model
and allowed model explicitly set. `QA_CITATION_DIAGNOSTIC=1` selects nine focused
repeats; `QA_CAPTURE_RAW=1` retains completed raw generation text in QA output,
without saving it as a completed user answer.
