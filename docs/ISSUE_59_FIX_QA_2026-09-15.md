## Environment and practical limits

Live runs use fresh **read-only production PostgreSQL** retrieval and the real
Vertex `gemini-3.6-flash` model with the existing 1,600-token cap. The new eDNA
summaries are rebuilt from current canonical rows and substituted **in memory**
for the two pilot retrieval documents. Production rows, embeddings, publication
pointers and service configuration were not changed. Ranking still uses the
existing production index; the refreshed index needs a deployment acceptance check.

Browser verification uses the built candidate frontend, actual candidate API
routes, synthetic retrieval/model responses, and isolated SQLite history. It
verified range navigation, the evidence inspector, audit wording, structured
failures, empty-scope abstention and applied dates. The initial local model
allowlist mismatch was corrected before acceptance. Browser date `fill` did not
persist values; native date entry and the applied-filter ledger verified the tested
intervals. These local browser checks are separate from the live cloud-model runs.

Citation checks do not determine whether every generated statement is scientifically
supported. The specific standards/calibration and abundance questions were reviewed;
these trials do not establish universal scientific correctness, exhaustively assess
all corpus records, or constitute a load/security benchmark. Some answers still use
broad or ambiguous prose (for example, “across both pipelines” for per-method totals).
Those limitations must not be represented as scientifically verified by the UI.

The full-suite sandbox run initially could not bind its localhost fixture servers;
the suite passed with that access. Full testing also caught a provenance validator
that rejected document version 3; version-aware validation and tamper regressions
were added before the final passing run. A repeat against the reused integration
database failed an empty-database assumption because earlier fixtures remained.
The final repeat against a fresh disposable database passed all 13 integration
tests; the disposable container was removed afterward.

## Reproduction and rollout

```sh
.venv/bin/python -m pytest -q
.venv/bin/python -m evaluation.qa.probe_chat_contract
node evaluation/qa/probe_markdown.cjs
npm --prefix frontend test
npm --prefix frontend run typecheck
npm --prefix frontend run build
node evaluation/qa/check_captured_markdown.cjs docs/ISSUE_59_FIX_QA_2026-09-15_RESULTS.json
```

Run PostgreSQL integration tests only against a disposable database with
`RUN_POSTGRES_INTEGRATION=1`. The configured cloud QA runner supports `QA_REPEATS=5`,
`QA_REFRESH_EDNA=1` and `QA_CAPTURE_RAW=1`; set `CHAT_MODEL` and
`ALLOWED_CHAT_MODELS` explicitly to the production model. It does not publish or
rebuild production data.

Follow the [release notes](RELEASE_NOTES_0.4.5.md) for the required retrieval,
embedding and provenance refresh. Keep issue #59 open until deployment and the
refreshed-corpus smoke checks are complete.
