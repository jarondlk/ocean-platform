## Assessment

and CI at the exact baseline commit pass. No new failing implementation gate
was identified. Chat-answer reliability has known, production-reproduced

and does not select a v0.6.0 implementation approach. The private cloud
inventory could not be refreshed because the saved GCP session requires
reauthentication. Production availability and anonymous access rejection were
checked today; corpus, traffic allocation and backup facts below are explicitly

The separate `/settings` page persists appearance/language preferences in this
browser through `frontend/lib/preferences.tsx`. Chat settings do not currently
use that store. Chat is a single-question/response workbench; persisted
interactions do not provide a multi-turn conversation settings lifecycle.

## Findings relevant to v0.6.0

### 1. Known answer-support defects remain — high priority

Issue #70 records production reproduction of a rare-taxon false denial and an
unsupported freshness claim, plus aggregate routing and response-focus defects.
The rare taxon is present in canonical data but absent from the top-ten assay
prose (`retrieval/edna_document_builder.py`), so matching a taxon in the retrieval
filter does not guarantee the prompt contains its exact supporting row.
Collection dates also do not establish provider publication or ingestion time.

This audit reproduced the routing cases without any live model call:

| Question | Current route |
| --- | --- |
| Can you summarize the ANEMONE database? | Scope clarification |
| Does a higher ANEMONE read count mean there are more fish? | Scope clarification |
| ANEMONEにはいくつのサンプルがありますか？ | Ordinary retrieval |
| Give a summary of ANEMONE data | Exact aggregation |

These defects are tracked, previously accepted release limitations. Source
controls alone will not fix them. Preserve them as explicit regression and
claim-support acceptance cases when deciding v0.6.0 scope.

### 2. Unrecognized settings are silently discarded — contract risk

`RetrieveRequest`/`ChatRequest` use Pydantic's default extra-field behavior.
Schema-level probes confirmed each of these is accepted with
`source_type=None` and the supplied fields discarded:

```json
{"query":"temperature","source_types":["ctd"]}
{"query":"temperature","source_types":[]}
{"query":"temperature","source_settings":{"ctd":{"bay":"O"}}}
```

Those are illustrative unsupported requests, not existing frontend payloads.
They demonstrate that adding checkboxes before the server understands their
contract could silently retrieve all sources, including when every source is
unchecked. Unknown `source_type` strings are also accepted instead of being
validated against a source registry. v0.6.0 needs explicit validation and
compatibility behavior, including a deliberate meaning for omitted versus
empty selection.

### 3. Some displayed generation settings are ineffective on Vertex — confirmed

The UI submits `repeat_penalty` and `num_ctx`; `_ollama_options` records them
under response `options.generation`. `VertexRuntime.chat` forwards neither.
A synthetic client probe with penalty `1.8` and context `32768` confirmed both
were present in reported options but absent from the provider configuration.

Provider-supported controls and requested/effective settings need distinct,
accurate presentation. Output-token limiting already reports the effective
Vertex cap and has regression coverage. This finding is about the ignored
penalty/context controls, not that tested cap.

### 4. Per-source filters require a new scope contract — implementation gap

The current flat contract is not independently scoped per source. Setting
provider, project, run, assignment method, taxon, sample kind or control status
implicitly restricts retrieval to eDNA when no family is specified; pairing
those fields with an explicit other family is rejected. Global bay/date and
coordinate filters apply to eligible documents across the request.

The server already supports more eDNA fields than chat exposes, including
project/run, method, taxon, classification, control status, coordinates and
explicit aggregation options. Existing CTD/metagenome/SST chat filters are
primarily document/sample/location/time scope. Station, depth, measurement
variable and metagenome-classifier controls are not established chat request
fields. Many documents summarize whole casts, samples or daily observations;
new finer controls must state whether they filter documents or recompute
evidence from canonical rows.

### 5. Every evidence path must obey source exclusion — acceptance requirement

Current single-source scope conservatively filters linked and supplementary
evidence, including mixed-family context. Generalizing it to a set requires
handling `covered_source_types`, analysis membership/environmental links,
exact-count routing, both ranked backends and the final supplied-evidence
manifest. A source checkbox cannot be enforced only in the initial search.

Exact aggregation currently supplies an immutable aggregate as analysis
context independently of `inject_analysis`, and analysis-ID requests resolve
their own environmental eDNA cohort. Clarify those control semantics before
presenting them as independent settings. Diagnostics and recorded effective
options must expose automatic narrowing, exclusions and actual answer mode.

### 6. Settings lifecycle and shared definitions are missing — product gap

There is no chat-specific validated persistence, versioned settings format,
source capability registry or shared frontend/backend settings definition.
The main page is 904 lines and `api/main.py` is 5,632 lines; adding more controls
will require care around the existing request/response/evidence boundary.
Persistence duration, reset behavior and account/browser scope are decisions
for the subsequent plan, not assumptions settled by this audit.

## Readiness conditions for the next discussion

The baseline passes its engineering gates and can support v0.6.0 development.
Before settling an approach, decide the source-selection semantics, supported
per-source filters, settings lifecycle, treatment of derived multi-source
evidence, provider capabilities and whether issue #70 fixes belong in this
milestone. Retain pre-ranking membership enforcement, deterministic abstention,
scientific classification rules, immutable provenance, role authorization and
the production external-job boundary as acceptance constraints.

Fresh private cloud inventory remains a separate outstanding verification
item until GCP access is renewed. No production readiness claim beyond the
recorded rollout and today's public probes is made here.
