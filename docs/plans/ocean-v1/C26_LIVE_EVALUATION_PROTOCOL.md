# C26 live evaluation protocol

Status: **Not run. Not ready to deploy.** This protocol describes later evidence collection; it does not authorize a provider call, cloud change, data transfer, scientific approval or release. C26's current executable runner uses synthetic local fixtures only. Beta hosting, authenticated independent sessions, Cloud Tasks/outbox/private invocation and the production retained-worker port/supervisor remain separate integrations.

## Preparation and immutable inputs

1. Obtain concrete authorization for the target, exact data/cohort, provider/model configuration, test budget and operations. Record independent project/resource/session identities from C24. Verify the legacy target is denied. The proposed beta origin is `https://beta.oceaninfobio.com`; it is not evidence of deployed DNS/TLS or an authorized target configuration.
2. Seal an explicit eligible one-way data copy through the C09 quarantine/import path. Preserve source/object hashes, publication/classification/relationship/operation versions and origin provenance. Record owner permissions and current policy revision. Do not use production traffic, shared accounts, automatic history import or live origin dependencies.
3. Write a shared question manifest *before* either implementation runs. Record exact question text/language, question ID, permissions, complete scope, canonical snapshot identity, fixture identity/hash, source revision and provider mode/provider/model/configuration. Native legacy and v1 wrapper IDs may differ; explicitly record both and independently verify the same sealed logical publication bytes. If scope, permissions, snapshot or provider differs, report an unmatched comparison as blocked.
4. Author the numerical/reference inventory oracle independently of generated answers. Record canonical object IDs, exact decimal numbers with entity/denominator/units, supported structured claims, required tasks, valid receipt IDs and expected completion/refusal/clarification. Preserve unknown values as unknown. Retain assessor identity and review scope; no automatic scientific approval is implied.

## Execution and observations

Run each authorized implementation in its independent service/session under the identical manifest. Save immutable raw requests, responses, durable run/events/steps, receipt hashes and retained provider responses before deriving metrics. Record provider/model versions, SDK/runtime versions, model parameters, UTC timestamps, elapsed timing, tool calls, retries, input/output tokens, billed cost/currency and measurement basis. Unknown token/cost values are null with basis `unknown`; a fixture value or no call is not measured zero billing. Keep externally supplied secrets and authentication codes out of receipts.

Evaluate these separately with `evaluation/system_acceptance.py` and the strict models in `schema/system_acceptance.py`:

- Complete authorized inventory membership, missing/unexpected IDs, whole-scope totals and denominator.
- Exact numerical parity against the independent oracle; preview size must not change the answer.
- Unsupported claims with an explicit complete structured-claim audit. Reviewing selected claim IDs does not establish arbitrary-prose factuality or scientific approval.
- Required-task completion and expected bounded refusal/clarification, including unresolved work.
- Citation validity against supplied retained evidence. Valid citations alone do not establish numerical correctness, supported claims or successful completion.
- Latency, tool use, tokens and cost with the measured/fixture/unknown basis preserved. Do not compare a paid/live run with scripted-provider timings as live quality evidence.

Retain English/Japanese incompatible geography/taxa/method questions, complete catalogue and late-page requests, known-zero versus unavailable/incomplete/unknown cases, hostile text/malformed actions, cancellation, duplicate delivery, interrupted committed steps, continuation, explicit refresh and access/role/source revocation. Reopen historical evidence under *current* authority. No exactly-once provider billing claim follows from application step idempotency.

## Hosted runtime and execution qualification

Run the C24 live gate list against the configured independent target: authenticated hosting/origin/session boundaries, IAM/network/storage/database/queue/credential isolation, queue/outbox/worker integration, backups/restores, observability, rollback and DNS/TLS. Preserve expected and observed denial evidence and the no-legacy-change ledger. C27 owns release rehearsal and operator acceptance.

C23's original Linux/gVisor observations retain their original source, host, failed/qualified scenarios and held-capacity limitations. They are not a current production-port run. A changed worker/port/image/containment source requires the corresponding fresh qualification. Verify exact hash-bound proposal approval, no network/credentials/host sockets/packages, whole-process-tree termination, admission/resource/output limits, deterministic declared seeds and durable validated experimental outputs. Keep experiment labels in every surface and export. Uncertain recovery must retain capacity rather than fabricate termination or release proof.

## Assessment and withdrawal

Every R01–R33/G0–G9 row retains passed/failed/blocked/not-run status, exact evidence identity/source, runtime, independent expected/actual results, gate owner and limitations. Missing observations never pass. Local preparation and current live release acceptance are separate fields. Keep original failed receipts immutable and record approved source supersessions; do not rewrite their source identity after repairs.

On a copied-source withdrawal, record the origin notification and explicitly revoke the destination copy through the documented destination procedure. Independent copies do not silently synchronize. Preserve held receipts/history according to current authority and retention rules. Stop advancement if a required gate fails; route its reproducible defect to its owning component and obtain scope expansion where required. Release promotion requires the actual acceptance gates and separately authorized deployment configuration, not a successful preparation report.
